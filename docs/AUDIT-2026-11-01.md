### Все пять специальных операций

В [SQL-схеме](../db/schema.sql) определены:

1. `lab1_organization_with_min_employees()` — один объект с минимальным количеством сотрудников.
2. `lab1_organizations_name_starts_with(prefix)` — массив по буквальному префиксу.
3. `lab1_organizations_type_greater_than(type)` — сравнение порядком `COMMERCIAL < GOVERNMENT < PRIVATE_LIMITED_COMPANY`, не алфавитом.
4. `lab1_merge_organizations(...)` — новая организация с суммой сотрудников, заданными пользователем именем и адресом.

**Нужно проговорить семантику объединения на защите:** текущая функция сохраняет исходные организации, копирует coordinates первой, суммирует оборот, берёт max rating/type, postalAddress = null. ## Исправления этого аудита

### 1. Асинхронные гонки в справочниках

В [references.html](../src/main/webapp/references.html):

- старый ошибочный ответ списка больше не затирает новый успешный результат;
- отмена/закрытие/Escape инвалидирует ожидающий запрос связей;
- старый 404 не закрывает окно удаления другого объекта;
- диалог открывается сразу со статусом загрузки; удаление недоступно до успешного получения связей;
- актуальность ответа проверяется и для успешного, и для ошибочного пути.

Четыре новые регрессии в [ui.test.cjs](../scripts/ui.test.cjs). Три воспроизведения до исправления: 25 passed / 3 failed; итог после исправления и дополнительного теста: 29 passed.

### 2. Уведомления не публикуются до подтверждённого commit

[OrganizationChangeNotifier](../src/main/java/ru/itmo/is/service/OrganizationChangeNotifier.java) раньше при исключении регистрации JTA callback переходил к немедленному broadcast: клиент мог перечитать старое состояние до commit или получить событие откатившейся операции. Теперь ошибка логируется без такого fallback; активная транзакция публикует только из `afterCompletion(STATUS_COMMITTED)`. Явный `STATUS_NO_TRANSACTION` допускает немедленную отправку. Добавлены [5 unit-тестов](../src/test/java/ru/itmo/is/service/OrganizationChangeNotifierTest.java).

Ограничение: при отказе регистрации уведомление пропускается. Для гарантированной доставки при инфраструктурных сбоях нужен transactional outbox/повторная сверка состояния, а не рассылка до commit.

### 3. Ошибка WebSocket не оставляет молча исключённого подписчика

[OrganizationWebSocket](../src/main/java/ru/itmo/is/websocket/OrganizationWebSocket.java) теперь закрывает проблемную сессию кодом 1011 при async send failure/onError, чтобы клиент запустил reconnect + full refresh. Синхронное исключение отправки одному клиенту не обрывает рассылку остальным. Добавлены [4 unit-теста](../src/test/java/ru/itmo/is/websocket/OrganizationWebSocketTest.java). Закрытие транспортного соединения best-effort; абсолютная доставка при отказе транспорта не обещается.

### 4. Документация

Добавлены этот аудит, [сравнение работ](COMPARISON-2026-11-01.md), исходники двух UML-диаграмм, выводы. В [инструкции Helios](HELIOS.md) отделён пользовательский факт запуска от неподтверждённого CRUD, описан API-only прогон без создания схем.

## Что ещё доработать

### Приоритет 1 — сквозная приёмка текущего WAR на Helios

HTTP 200 страницы входа не доказывает ни возможность записи аккаунта, ни доступность JDBC, ни наличие функций в правильной схеме. Обновлённый WAR **не развёрнут** этим аудитом. После ручного обновления и перезагрузки вкладок выполнить сценарий ниже. Полный DatabaseIT нельзя направлять в рабочую схему: тесты делают TRUNCATE.

### Приоритет 2 — два конкурентных сценария БД

Это выводы из чтения кода и расписания операций, **не воспроизведённые в данном аудите интеграционные тесты**. Исправления блокировок намеренно не внесены без проверки настоящего PostgreSQL.

**Location-rebind против создания/перепривязки Organization.** [ReferenceDataRepository:106–119](../src/main/java/ru/itmo/is/repository/ReferenceDataRepository.java#L106-L119) сначала отдельным SQL повышает версии зависимых организаций, затем меняет Address.town. Между statements другой запрос может создать организацию с этим адресом и получить старый town. После commit переназначения её вложенный объект изменится без повышения version; старая форма не обязательно получит 409. `@Transactional` при READ COMMITTED само по себе не закрывает окно.

Направление исправления: единый transaction-scoped протокол блокировок **до чтения сущностей** во всех изменяющих сервисах. Для небольшой лабораторной возможен общий PostgreSQL advisory lock: shared для обычных изменений, exclusive для удаления справочников, всегда первым шагом и без lock upgrade. Прямые SQL-writers также должны соблюдать договорённость. Локальный `LOCK TABLE` только в replaceLocation опасен новым deadlock из-за разного порядка записи Organization/Address. Нужен двухтранзакционный тест с барьерами, а также проверка, что JPA не возвращает старый объект из persistence context.

**Согласованность источников merge.** [schema.sql:203–208](../db/schema.sql#L203-L208) читает две организации двумя SELECT внутри VOLATILE-функции. При READ COMMITTED между ними может вклиниться commit конкурентного изменения; сумма получится из разных снимков. Лучше прочитать оба источника одним statement либо заблокировать их в стабильном порядке ID до расчёта. Выбор зависит от согласованной семантики объединения. Проверить конкурентно с изменением/удалением исходников; один лишь тест одновременных merge с одинаковым idempotency key это не проверяет.

### Приоритет 3 — более точные SQL-ошибки

[ApiExceptionMapper:21–25](../src/main/java/ru/itmo/is/exception/ApiExceptionMapper.java#L21-L25) превращает SQLSTATE 22*/23* в общее сообщение о лимите/связи. Например, при addEmployee для Long.MAX_VALUE полезно сообщить именно о невозможности увеличить количество сотрудников, а при merge — о переполнении суммы. Нужны безопасные сообщения по whitelist SQLSTATE/известным ограничениям, без вывода произвольного SQL, внутренних исключений или секретов.

## Сценарий приёмки перед защитой

Использовать только отдельные тестовые записи; два независимых браузерных профиля/пользователя, а не просто вкладки с общей сессией.

1. Регистрация → выход → вход; повторный логин отклоняется, неверный пароль не авторизует. Проверить сохранение аккаунта после планового перезапуска.
2. Создать организацию A с новыми Coordinates/Address/Location, postalAddress = null. Во втором клиенте она появляется без F5. Создать B с существующими справочниками.
3. Найти по ID и сверить все связанные поля; изменить из таблицы и из карточки. Открыть старую форму в другом клиенте: после чужого изменения её сохранение должно дать 409 и сохранить черновик.
4. Проверить `0`, отрицательное, дробное в int/long, пустое имя; допустимый пустой zipCode; маленький положительный turnover `1e-8`; точный long больше 2^53.
5. Создать более 10 тестовых объектов; проверить страницы, удаление последней строки, сортировку и неполный фильтр каждой доступной строковой колонки, буквальные `%` и `_`.
6. Удалить используемый справочник: без замены отказ; выбрать замену; связи A/B обновляются, оригинал исчезает. Повторить для Coordinates, Address (обе роли), Location. Не выбирать реальные пользовательские объекты для этих удалений.
7. Выполнить пять спецопераций. Для merge проверить новую организацию/сумму/адрес/согласованную судьбу исходников. Для addEmployee — +1 и обновление версии. Во втором клиенте проверить результаты и список.
8. Отключить/восстановить сеть второго клиента: статус соединения и полная синхронизация после reconnect; изменения, сделанные во время разрыва, не потеряны.
9. Удалить тестовые организации, затем только принадлежащие проверке адреса/координаты/города. Проверить, что реальные данные не затронуты.

API-only автоматизация и ограничения cleanup/регистрации описаны в [инструкции Helios](HELIOS.md). Эта последовательность — план проверки, а не список уже успешно пройденных пунктов.

Перед сдачей отрендерить UML локально, вставить изображения и выводы из README, указать автора/группу и приложить репозиторий/исходники. Не писать в выводах «все проверки Helios пройдены», пока это не выполнено.

На защите полезно объяснить на собственном коде:

- **Layered architecture, Service Layer, Repository, DTO/Mapper, Dependency Injection** — зачем отделены HTTP, транзакции и хранение.
- **Jakarta EE** — спецификации/контейнер; Servlet, JAX-RS, CDI, JPA, JTA, Validation, WebSocket. CDI bean не равен entity и не равен EJB.
- **CDI** — `@Inject`, scope, proxy, жизненный цикл; `@ApplicationScoped` не делает изменяемые поля автоматически потокобезопасными.
- **ORM/JPA** — EntityManager, persistence context, managed/detached, flush ≠ commit, owning side, cascade, fetch, optimistic/pessimistic locking.
- **Hibernate vs EclipseLink** — разные реализации JPA с собственными расширениями; в этом проекте явно выбран EclipseLink. Native SQL требует согласования с JPA cache/version.
- **Jakarta Data** — спецификация декларативных репозиториев; не синоним JPA и не обязательная часть Jakarta EE 10 этого проекта. Здесь репозитории написаны вручную.
- **Spring / Boot / Data** — framework/DI; автоконфигурация и starters; абстракции репозиториев. Это разные уровни, а не три названия ORM. Их знание требуется на защите, но использование не требуется вашим вариантом.
