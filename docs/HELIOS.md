# Ручное развёртывание на Helios

Пользователь: `s465142`. SSH: `helios.cs.ifmo.ru:2222` (также `se.ifmo.ru`).
Приложение слушает `127.0.0.1:46514`, SSH-туннель открывает его на `localhost:18080`.
Локальные Docker-контейнеры для этого не нужны.

**Статус на 1 ноября 2026:** по сообщению владельца приложение запущено на Helios,
страница входа отвечала HTTP 200. Это ещё не проверка регистрации, JDBC и операций с данными.
В текущем аудите туннель `localhost:18080` был недоступен, SSH без интерактивного пароля
отклонён; по выбору владельца выполнены только локальные проверки, сервер не изменялся.
Сам скрипт повторно проверен синтаксически и 19 тестами с поддельными Java/psql.
Отключение Hazelcast ранее проверено по реализации JAR Payara Micro 6.2025.11.

## 1. На своём компьютере, из каталога проекта

Если текущий WAR уже собран, первую команду можно пропустить. JAR-файлы загружайте
после сборки: `mvn clean` удаляет содержимое target.

```bash
mvn clean package
curl -fL https://repo.maven.apache.org/maven2/fish/payara/extras/payara-micro/6.2025.11/payara-micro-6.2025.11.jar -o target/payara-micro.jar
curl -fL https://repo.maven.apache.org/maven2/org/postgresql/postgresql/42.7.7/postgresql-42.7.7.jar -o target/postgresql.jar

ssh -p 2222 s465142@helios.cs.ifmo.ru 'mkdir -p ~/is-lab1'
scp -P 2222 target/is-lab1.war target/payara-micro.jar target/postgresql.jar db/schema.sql scripts/helios-start.sh s465142@helios.cs.ifmo.ru:~/is-lab1/
```

Пароль SSH вводится только в терминале. При ошибке системного SSH-конфига
`Bad owner or permissions ...20-systemd-ssh-proxy.conf` добавьте `-F /dev/null`
к вызовам ssh/scp. Это не отключает проверку ключа сервера.

## 2. На Helios

```bash
ssh -l s465142 -p 2222 se.ifmo.ru
sh
cd "$HOME/is-lab1"
chmod 600 "$HOME/.pgpass"
command -v awk
command -v psql
```

Для запуска на Helios нужны стандартные `sh`, `awk`, `stat`, а также psql и Java 17 либо 21.
**Python на Helios не нужен.** Скрипт сначала проверяет
`/usr/local/openjdk17/bin/java`, затем `java` из PATH. При необходимости задайте
`export JAVA_BIN=/путь/к/java17/bin/java`.

В домашнем каталоге Helios должен находиться `.pgpass` с записью, подходящей для
`pg:5432:studs:s465142`; запись `*:*:*:s465142:пароль` тоже подходит.
Не печатайте этот файл и не отправляйте его в чат. Скрипт читает пароль напрямую
в окружение Java; не добавляет его в аргументы процесса, скрипты или конфигурационные файлы.
Поддерживаются экранированные `\:` и `\\`; применяется первая подходящая запись.

Для фонового запуска:

```bash
umask 077
nohup sh ./helios-start.sh > payara.log 2>&1 < /dev/null &
echo $! > payara.pid
tail -f payara.log
```

`Ctrl+C` здесь завершает только просмотр журнала. В журнале дождитесь успешного
развёртывания приложения и HTTP-listener на порту 46514.

Скрипт [helios-start.sh](../scripts/helios-start.sh):
- использует PostgreSQL `pg/studs` и личную схему `s465142`, а не общую `public`;
- проверяет существующую схему и права USAGE/CREATE без выполнения CREATE SCHEMA; создаёт схему только при её отсутствии и наличии права CREATE в базе;
- повторно применяет [schema.sql](../db/schema.sql), не удаляя данные;
- передаёт ту же схему JDBC через `currentSchema`;
- хранит аккаунты приложения отдельно в `~/is-lab1/accounts/users.properties` с закрытыми правами;
- полностью отключает Hazelcast флагом `--nohazelcast` до старта сервера и настраивает HTTP только на loopback;
- останавливается при ошибке чтения пароля, несовместимой Java или ошибке миграции.

### Если Hazelcast пытается подключиться к чужому кластеру

На общем Helios одного `--noCluster` недостаточно: Hazelcast остаётся включённым.
Используйте **`--nohazelcast` вместо `--noCluster`, не оба флага вместе**.
В используемой версии ветка `noCluster` имеет приоритет над `noHazelcast`; сочетание
флагов не даёт полного отключения. Исправленный скрипт уже учитывает это.
Это не ошибка SSH-туннеля: без успешного старта сервера порт 46514 будет недоступен.

При обновлении достаточно заново передать скрипт, WAR пересобирать не нужно:

```bash
# На своём компьютере из каталога проекта:
scp -P 2222 scripts/helios-start.sh s465142@helios.cs.ifmo.ru:~/is-lab1/
# Затем на Helios:
cd "$HOME/is-lab1"
sh ./helios-start.sh
```

Ручной запуск только `java -jar ... --noCluster` пропускает также настройку аккаунтов,
миграцию БД и JDBC-драйвер. Для текущего приложения обязательно задаётся
`AUTH_USERS_FILE` — это делает скрипт.

### Если выводится permission denied for database studs

Права CREATE в базе нужны для создания новой схемы, но не для использования уже
существующей схемы с правами USAGE/CREATE. Даже CREATE SCHEMA IF NOT EXISTS может
проверять право CREATE в базе до проверки наличия схемы. Исправленный скрипт сначала
проверяет наличие схемы и не требует этого права для существующей схемы.

[Инструкция другого курса](https://github.com/CandyGoose/Database_SE/blob/8fabc2ba2f3283e28f0a3dc02e8581b84014c4dc/README.md)
подтверждает подключение `psql -h pg -d studs` и создание таблиц без предварительного
CREATE SCHEMA. Она не устанавливает имя доступной схемы именно для вашей учётной записи.
Проверьте реальные настройки на Helios (пароль не выводится):

```bash
psql -X -h pg -d studs -U s465142
```

В консоли psql:

```sql
SELECT current_user, current_schema(), current_setting('search_path') AS search_path;
SELECT nspname AS schema, pg_get_userbyid(nspowner) AS owner,
       has_schema_privilege(oid, 'USAGE') AS usage_ok,
       has_schema_privilege(oid, 'CREATE') AS create_ok
FROM pg_namespace
WHERE nspname NOT LIKE 'pg_%' AND nspname <> 'information_schema'
  AND has_schema_privilege(oid, 'USAGE')
ORDER BY nspname;
```

Если прежние данные находятся в другой вашей доступной схеме, согласованно задайте
`DB_SCHEMA` перед запуском. Не переключайтесь на чужую или общую public вслепую.
Если нет ни подходящей существующей схемы, ни права создать новую, нужно обратиться
к администратору БД. Скрипт в этом случае выводит права и не запускает миграцию.

Проверка на Helios:

```bash
curl -I http://127.0.0.1:46514/is-lab1/login.html
```

Ожидается HTTP 200. Если `curl` отсутствует, можно использовать `fetch -qo -`
или проверить через туннель на следующем шаге.

## 3. В отдельном терминале своего компьютера

```bash
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -L 127.0.0.1:18080:127.0.0.1:46514 -p 2222 s465142@helios.cs.ifmo.ru
```

Оставьте этот терминал открытым. В браузере откройте:

**http://localhost:18080/is-lab1/login.html**

Зарегистрируйтесь и проверьте создание организации. Для автоматической проверки HTTP
в другом локальном терминале:

```bash
curl -I http://localhost:18080/is-lab1/login.html
```

Туннель останавливается `Ctrl+C`. Для остановки приложения на Helios сначала
посмотрите процесс и убедитесь, что это именно Payara вашего проекта:

```bash
ps -p "$(cat payara.pid)" -o pid,args
# Только после проверки PID и команды:
kill "$(cat payara.pid)"
```

Не используйте `killall java`: на общем сервере это может затронуть другие работы.
При повторном развёртывании сначала остановите своё приложение, затем копируйте новый WAR
и схему и снова выполняйте запуск. Сам SSH-туннель не запускает серверное приложение.

## Обновление после исправлений конкурентности и merge

Сначала **остановите старую версию приложения**, затем передайте вместе новый WAR
и [SQL-схему](../db/schema.sql). Скрипт запуска применит функции, включая новый
`lab1_lock_writes`, в существующей схеме `s465142`. Без обновления SQL новый WAR
не сможет выполнять изменяющие операции. Не оставляйте старый экземпляр работающим
параллельно: он не соблюдает новый протокол блокировок.

После запуска перезагрузите вкладки. Новое объединение **удаляет обе исходные
организации**, а не сохраняет их. Подробности и результаты локального PostgreSQL/
Payara-прогона — в [отчёте исправлений](CONCURRENCY-FIXES-2026-11-01.md).
Эти изменения на Helios помощником не развёртывались.

## Обновление backend от 2 ноября

Новый WAR требует также таблицу `api_idempotency`: передавайте вместе WAR и
[SQL-схему](../db/schema.sql), затем запускайте прежний скрипт. Таблица создаётся
в существующей схеме `s465142`, новые схемы/расширения не нужны.
Пользовательские организации/аккаунты сохраняются; старый in-memory retry-cache
перенести невозможно. Повторы новых запросов с ключом теперь переживают рестарт и
новый вход, без общего JVM-монитора. История автоматически не очищается.

Даты POST/GET приведены к микросекундам; список и total получают один snapshot.
Авторизация: 30/мин по username/операции, 120/мин по фактическому IP, 1000/мин по
процессу; клиенты через один SSH-туннель могут разделять IP-предел.
[Полный отчёт и результаты проверок](BACKEND-FIXES-2026-11-02.md).
На Helios эти изменения помощником не применялись.

## Проверка данных через туннель (после разрешения владельца)

**Не запускайте полный `mvn -Pintegration verify` против Helios.**
[DatabaseIT](../src/test/java/ru/itmo/is/DatabaseIT.java) и
[DatabaseConcurrencyIT](../src/test/java/ru/itmo/is/DatabaseConcurrencyIT.java)
создают/удаляют временные схемы, а `s465142` не имеет права создавать схемы в `studs`.
Не заменяйте временную схему на рабочую: внутри этих тестов есть TRUNCATE.
[MutationApiIT](../src/test/java/ru/itmo/is/MutationApiIT.java) использует JDBC-перепривязку
одновременно с HTTP; [IdempotencyIT](../src/test/java/ru/itmo/is/IdempotencyIT.java)
устанавливает временное CHECK-ограничение для моделирования отказа сохранения ответа;
[PaginationIT](../src/test/java/ru/itmo/is/PaginationIT.java) создаёт временную схему.
Эти классы предназначены **только для отдельного тестового экземпляра**, не Helios.

Для проверки приложения отдельно можно запустить только HTTP/WebSocket-тесты
из локального каталога проекта. Сначала в браузере зарегистрируйте отдельного
тестового пользователя и убедитесь, что туннель открыт. Используйте **пароль
этого аккаунта приложения**, не SSH/БД-пароль. В локальном Bash:

```bash
export TEST_BASE_URL=http://127.0.0.1:18080/is-lab1
read -r -p 'Логин тестового аккаунта приложения: ' TEST_AUTH_USER
read -r -s -p 'Пароль аккаунта приложения: ' TEST_AUTH_PASSWORD
printf '\n'
export TEST_AUTH_USER TEST_AUTH_PASSWORD
mvn -Pintegration -Dit.test=ApiIT verify
unset TEST_AUTH_PASSWORD TEST_AUTH_USER
```

[ApiIT](../src/test/java/ru/itmo/is/ApiIT.java) создаёт собственные организации и
справочники, проверяет версии/перепривязки/конкурентные запросы/WebSocket и пытается
удалить тестовые данные. Запускайте без параллельной ручной работы пользователей:
тестовые объекты видны всем; не связывайте свои данные с ними. После сбоя проверьте
остатки: cleanup отправляет DELETE, но не проверяет коды всех ответов.
Прямое подключение к БД и TEST_DB_* для этого выбранного класса не нужны.

Отдельная автоматическая проверка регистрации:

```bash
mvn -Pintegration -Dit.test=RegistrationIT verify
```

Она требует только TEST_BASE_URL и **оставляет четыре новых аккаунта** за прогон
(три последовательных и один конкурентный). API удаления пользователей нет.
Не запускайте её без согласия владельца; в общей рабочей среде лучше вручную
проверить один тестовый аккаунт, повторный логин, неверный пароль и выход.

Ни одна из этих удалённых проверок не выполнялась в аудите 1 ноября.
Сценарий приёмки двумя браузерами приведён в [отчёте аудита](AUDIT-2026-11-01.md).
