## 4. Подтверждённые недочёты

Приоритеты: **P2** — стоит исправить следующим небольшим этапом, нормальный сценарий обычно работает, но крайний ломается; **P3** — малое неудобство/валидационный край. Найденные проблемы не исправлялись в ходе аудита.

### 4.1. P2 — запоздалый DELETE закрывает чужой новый диалог

- Источник: [index:728–741](../src/main/webapp/index.html#L728-L741). У диалога удаления нет cancel-guard, removeOrg не проверяет deleting, завершение confirmDelete работает с общим состоянием.
- Сценарий: DELETE #1 ждёт ответа → Escape закрывает окно → открыть удаление #2 → приходит ответ #1 → закрывается новое окно #2 и сбрасывается deleteId.
- Последствие: потеря текущего намерения пользователя; старый error также может попасть в новый диалог. **Это не доказательство ошибочного удаления #2**: в воспроизведении #2 остался в данных.
- Проверено не только моделью DOM: **нативный Escape настоящего Chrome**. [Лог](../review-artifacts/audit-2026-11-03/browser-edge-repro.log#L1), [repro](../review-artifacts/audit-2026-11-03/browser-edge-repro.cjs).
- Исправление: запретить cancel/смену цели во время deleting и/или привязать completion к локальному target/generation, как уже сделано для других диалогов.

### 4.2. P2 — ошибка загрузки карточки выводится за модальным окном

- Источник: [index:363–393](../src/main/webapp/index.html#L363-L393). Для GET 503/сетевого отказа viewer остаётся открытым с «Загрузка…», а showError пишет во внешний #error.
- Последствие: пользователь видит зависшую загрузку; ошибка находится под backdrop, а не внутри активного окна.
- **Подтверждено настоящим Chrome** с перехваченным GET 503: [лог](../review-artifacts/audit-2026-11-03/browser-edge-repro.log#L2), [скриншот](../review-artifacts/audit-2026-11-03/viewer-get503.png).
- Исправление: локальный error/retry в viewer; при неудачном refresh не уничтожать уже загруженные сведения.

### 4.3. P2 — окно гонки WebSocket при выходе пользователя

- Источники: [onOpen:19–24](../src/main/java/ru/itmo/is/websocket/OrganizationWebSocket.java#L19-L24), [sessionDestroyed:19–23](../src/main/java/ru/itmo/is/security/AuthSessions.java#L19-L23), [broadcast:64–74](../src/main/java/ru/itmo/is/websocket/OrganizationWebSocket.java#L64-L74).
- Сценарий: onOpen проверил действительный token → logout/expiry удалил token и закрыл уже известные sockets → onOpen добавил новый socket после прохода closeToken → broadcast больше не проверяет token.
- **Детерминированно подтверждено** на неизменённых production-классах, пауза latch в getUserProperties строго между valid и add: [Java repro](../review-artifacts/audit-2026-11-03/WebSocketLogoutRepro.java), [лог](../review-artifacts/audit-2026-11-03/websocket-logout-repro.log).
- Последствие ограничено **метаданными событий type/id после выхода**. Доступ к защищённым REST-карточкам этим тестом не продемонстрирован и не заявляется. Это узкая гонка, не общий обход авторизации.
- Исправление: согласовать регистрацию/отзыв socket и token (двухфазная регистрация с повторной проверкой/общий registry), а перед delivery прекращать подписку с отозванным token. Добавить latch-регрессию, а не тест на случайный тайминг.

### 4.4. P2 — изменённая форма после неопределённого исхода POST сохраняет старый retry-key

- Источники: [save:701–706](../src/main/webapp/index.html#L701-L706) и [guard:40–50](../src/main/java/ru/itmo/is/service/OrganizationCreationGuard.java#L40-L50).
- Сценарий: создание закоммичено, но ответ потерялся → пользователь меняет название и снова сохраняет → отправляется новое тело с прежним ключом → backend правильно возвращает 400 «already used with another request». Пока форму не переоткрыть, исправленное тело с этим ключом не сохранится.
- UI-последовательность подтверждена fixture с **явно моделированной потерей ответа после commit**; серверный контракт same-key/different-payload отдельно проверен настоящими Payara/PostgreSQL: [fixture log:2](../review-artifacts/audit-2026-11-03/frontend-targeted-repro.log#L2), [HTTP log](../review-artifacts/audit-2026-11-03/api-edge-contracts.log).
- Это **не дефект атомарности серверной идемпотентности** и не доказанная повторная запись. Недостаточна логика восстановления UI.
- Исправление: хранить immutable snapshot тела и ключа для uncertain retry и сначала выяснять исход старого запроса. Не выдавать бездумно новый ключ после любого network error — это как раз может создать дубль уже выполненной операции.

### 4.5. P2 — загрузка списка выбора несколькими offset-страницами может потерять существующий ID

- Источники: [special:122–134](../src/main/webapp/special.html#L122-L134), [fillSelect:73–80](../src/main/webapp/app.js#L73-L80).
- Сценарий на 201 записи: выбран ID 101 → page0 снят → параллельно удалён ID 1 → следующая страница начинается с offset 100 и пропускает живой ID 101 → fillSelect очищает выбор и ошибочно пишет, что #101 удалён.
- Подтверждено управляемым fixture: [repro](../review-artifacts/audit-2026-11-03/frontend-targeted-repro.cjs#L55-L68), [лог:5](../review-artifacts/audit-2026-11-03/frontend-targeted-repro.log#L5). Удаление между HTTP-страницами моделировано явно; это не тест единого PostgreSQL snapshot.
- Следующий WS refresh может вернуть option, но первоначальный выбор уже утрачен. При небольшом наборе ≤100 объектов этот конкретный сценарий не возникает.
- Исправление: стабильный selector endpoint/поиск или keyset traversal; как минимум перед очисткой выбранного ID перепроверять его отдельным GET. Dedup сам по себе пропущенную запись не восстановит.

### 4.6. P3 — валидатор и payload расходятся для leading-zero long

- Источники: [Lab.number:85–89](../src/main/webapp/app.js#L85-L89), [payload:672](../src/main/webapp/index.html#L672), [RequestParser:97–102](../src/main/java/ru/itmo/is/dto/RequestParser.java#L97-L102).
- `00000000000000000001` — валидный positive BigInt, но payload отправляет исходные 20 цифр, а parser принимает строковые long максимум из 19 цифр. UI считает форму валидной, сервер отвечает 400.
- Подтверждены UI fixture и реальный HTTP 400; каноническое `1` успешно создаёт объект: [логи](../review-artifacts/audit-2026-11-03/api-edge-contracts.log).
- Исправление: использовать возвращаемую Lab.number каноническую десятичную строку в payload, не Number(), чтобы не потерять long-точность.

- Постепенно вынести JS из [index](../src/main/webapp/index.html) в модули API/state/dialogs. Файл около 900 строк — уже неудобен для сопровождения, но React не обязателен.
- Для больших наборов добавить серверный поиск/порционную загрузку справочников и списков выбора: сейчас они загружаются целиком и перебираются при обновлениях. Без нагрузочного измерения не называем это уже наступившим bottleneck.
- Описать API/ошибки/opaque version/idempotency в OpenAPI или компактной спецификации; после роста SQL ввести версии миграций. Это полезные практики из чужих проектов, а не незакрытые обязательные функции 1364.

### Если приложение будет использоваться дольше лабораторной

- Политика хранения/квот для api_idempotency: сейчас история намеренно бессрочная. Удаление записей сокращает гарантию replay, поэтому не добавлять незаметный TTL.
- При переходе к нескольким экземплярам — перенести аккаунты из файлового UserStore в общий согласованный store и согласовать rate limiting. Текущая идемпотентность между JVM не делает весь auth-контур распределённым.
- Определить минимальную политику паролей (сейчас пустой допускается), transport/cookie policy для реального HTTPS и мониторинг. PBKDF2 уже есть; копировать чужой простой SHA или требование «уникального пароля» не нужно.
