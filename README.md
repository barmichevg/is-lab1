# Лабораторная работа 1

**Вариант:** `1364`

## Задание

Реализовать информационную систему, которая позволяет взаимодействовать с объектами класса `Organization`, описание которого приведено ниже:

```java
public class Organization {
    private int id; // Значение поля должно быть больше 0, значение этого поля должно быть уникальным, значение этого поля должно генерироваться автоматически
    private String name; // Поле не может быть null, строка не может быть пустой
    private Coordinates coordinates; // Поле не может быть null
    private java.time.LocalDateTime creationDate; // Поле не может быть null, значение этого поля должно генерироваться автоматически
    private Address officialAddress; // Поле не может быть null
    private float annualTurnover; // Значение поля должно быть больше 0
    private long employeesCount; // Значение поля должно быть больше 0
    private Integer rating; // Поле не может быть null, значение поля должно быть больше 0
    private OrganizationType type; // Поле не может быть null
    private Address postalAddress; // Поле может быть null
}

public class Coordinates {
    private int x;
    private int y;
}

public class Address {
    private String zipCode; // Поле не может быть null
    private Location town; // Поле не может быть null
}

public class Location {
    private Double x; // Поле не может быть null
    private Double y; // Поле не может быть null
    private int z;
    private String name; // Строка не может быть пустой, поле не может быть null
}

public enum OrganizationType {
    COMMERCIAL,
    GOVERNMENT,
    PRIVATE_LIMITED_COMPANY;
}
```

Разработанная система должна удовлетворять следующим требованиям:

- Основное назначение информационной системы — управление объектами, созданными на основе заданного в варианте класса.
- Необходимо, чтобы с помощью системы можно было выполнить следующие операции с объектами: создание нового объекта, получение информации об объекте по ИД, обновление объекта (модификация его атрибутов), удаление объекта. Операции должны осуществляться в отдельных окнах (интерфейсах) приложения. При получении информации об объекте класса должна также выводиться информация о связанных с ним объектах.
- При создании объекта класса необходимо дать пользователю возможность связать новый объект с объектами вспомогательных классов, которые могут быть связаны с создаваемым объектом и уже есть в системе.
- Выполнение операций по управлению объектами должно осуществляться на серверной части (не на клиенте), изменения должны синхронизироваться с базой данных.
- На главном экране системы должен выводиться список текущих объектов в виде таблицы (каждый атрибут объекта — отдельная колонка в таблице). При отображении таблицы должна использоваться пагинация (если все объекты не помещаются на одном экране).
- Нужно обеспечить возможность фильтровать/сортировать строки таблицы, которые показывают объекты (по значениям любой из строковых колонок). Фильтрация элементов должна производиться по неполному совпадению.
- Переход к обновлению (модификации) объекта должен быть возможен из таблицы с общим списком объектов и из области с визуализацией объекта (при её реализации).
- При добавлении/удалении/изменении объекта он должен автоматически появиться/исчезнуть/измениться в интерфейсах у других пользователей, авторизованных в системе.
- Если при удалении объекта с ним связан другой объект, связанные объекты должны быть связаны с другим объектом (по выбору пользователя), а изначальный объект удалён.
- Пользователи должны иметь возможность просмотра всех объектов. Для модификации объекта должно открываться отдельное диалоговое окно. При вводе некорректных значений в поля объекта должны появляться информативные сообщения о соответствующих ошибках.

В системе должен быть реализован отдельный пользовательский интерфейс для выполнения специальных операций над объектами:

- Вернуть один (любой) объект, значение поля `employeesCount` которого является минимальным.
- Вернуть массив объектов, значение поля `name` которых начинается с заданной подстроки.
- Вернуть массив объектов, значение поля `type` которых больше заданного.
- Объединить организации, создав новую и зачислив в неё всех сотрудников двух исходных. Пользователь должен указать исходные организации, имя и адрес новой организации.
- Добавить нового сотрудника в организацию с указанным `id`.

Представленные операции должны быть реализованы в качестве функций БД, которые необходимо вызывать из уровня бизнес-логики приложения.

Особенности хранения объектов

- Организовать хранение данных об объектах в реляционной СУБД PostgreSQL. Каждый объект, с которым работает ИС, должен быть сохранён в базе данных.
- Все требования к полям класса (указанные в виде комментариев к описанию классов) должны быть выполнены на уровне ORM и БД.
- Для генерации поля `id` использовать средства базы данных.
- Для подключения к БД на кафедральном сервере использовать хост `pg`, имя базы данных — `studs`, имя пользователя/пароль совпадают с таковыми для подключения к серверу.

Особенности взаимодействия с пользователем

- Система должна реагировать на некорректный пользовательский ввод, ограничивая ввод недопустимых значений и информируя пользователей о причине ошибки.
- Переходы между различными логически обособленными частями системы должны осуществляться с помощью меню.
- При добавлении/удалении/изменении объекта он должен автоматически появиться/исчезнуть/измениться в области у всех других клиентов.

Требования к разработке

- В качестве основы для реализации ИС необходимо использовать Jakarta EE, CDI beans.
- Для создания уровня хранения необходимо использовать JPA + EclipseLink.
- Разные уровни приложения должны быть отделены друг от друга, разные логические части ИС должны находиться в отдельных компонентах.

## Запуск и обновление

Версия приложения: **0.7.1**. Требуются Java 17, Maven, Payara 6 и PostgreSQL.

Для запуска на Helios без локального Docker: [инструкция, скрипт и SSH-туннель](docs/HELIOS.md).

### Docker: первый запуск и обновление

```bash
mvn clean package
docker compose up -d --wait postgres
./scripts/apply-db.sh
docker compose up -d --force-recreate --wait payara
```

Откройте <http://localhost:8080/is-lab1/login.html> и зарегистрируйтесь.
`--wait` ждёт HTTP 200 страницы входа, а не только старта процесса Payara.

Сеть проекта использует `172.30.136.0/24`, чтобы не пересекаться с VPN-интерфейсами
на `172.18.0.x`. При необходимости задайте другую свободную подсеть переменной
`LAB1_DOCKER_SUBNET`. После изменения подсети существующую сеть нужно пересоздать:

```bash
docker compose down && docker compose up -d --wait
```

Не добавляйте `-v` к `down`: без этого флага том PostgreSQL и данные сохраняются.

`accounts-init` автоматически готовит каталог `auth-data` для UID 1000, от которого
работает Payara: каталог получает права `0700`, существующий файл аккаунтов — `0600`.
Только этот короткоживущий сервис работает от root; само приложение не меняет пользователя.
Существующие аккаунты сохраняются. Не удаляйте `auth-data` при обновлении и не задавайте
каталогу права `0777`.

Повторно применяйте [SQL-схему](db/schema.sql) при обновлении: существующий том PostgreSQL
не выполняет init-скрипт заново. Схема идемпотентна и сохраняет данные; в частности,
она добавляет версию существующим организациям для защиты от устаревших изменений.
Пересоздание Payara в команде выше также подключает актуальный WAR после новой сборки.
После обновления перезагрузите открытые вкладки приложения.
Список исправлений и результаты проверок: [исправления от 20 октября](docs/FIXES-2026-10-20.md).

Вне Docker задайте `DB_URL`, `DB_USER`, `DB_PASSWORD` и `AUTH_USERS_FILE`.
Каталог и файл аккаунтов должны быть доступны на запись пользователю Payara.
Файл создаётся при первой регистрации; заранее создать аккаунт можно с помощью
[скрипта создания пользователя](scripts/create-user.py).
Для кафедральной БД используйте [скрипт pg/studs](scripts/apply-db-pg.sh).

### Конкурентное редактирование

API возвращает `version` организации десятичной строкой. Запрос `PUT` должен передавать
эту же версию из первоначально загруженной карточки. Если другой клиент уже изменил
организацию, добавил сотрудника или перепривязал её справочники, сервер возвращает
`409 Conflict`, не перезаписывая данные. Черновик формы остаётся доступен пользователю.
При создании версия не передаётся. Версия — непрозрачный для клиента счётчик:
нужно возвращать полученное значение, не вычисляя его самостоятельно.

### Перепривязка и объединение

Все изменяющие сервисы получают блокировку транзакции **до чтения сущностей**.
Обычные изменения используют shared advisory lock PostgreSQL; удаление справочника
и merge — exclusive lock в пределах текущей схемы. Поэтому новая организация либо
получает уже обновлённый город, либо попадает в повышение version при последующей
перепривязке. Общий JPA-кэш отключён, чтобы не возвращать старые Address/Location.

Merge теперь **заменяет две исходные организации одной новой**: сотрудники и оборот
суммируются, исходники удаляются в той же транзакции. Координаты берутся у первой,
rating/type — максимальные, postalAddress отсутствует. Справочники исходников не
удаляются. Ошибка/переполнение откатывает всю операцию. Параллельное объединение
уже удалённых источников получает 404, а не создаёт вторую копию сотрудников.

Важно: прямые SQL-записи должны соблюдать тот же протокол `lab1_lock_writes`.
Нельзя смешивать старую и новую версии приложения во время обновления.
[Подробности, SQL-ошибки и результаты регрессий](docs/CONCURRENCY-FIXES-2026-11-01.md).

### Устойчивые повторы, авторизация и списки

`X-Idempotency-Key` для create/merge/add-employee хранится в PostgreSQL вместе
со снимком ответа, в одной транзакции с изменением. Область ключа — username + операция,
а не Session ID: повтор работает после нового входа/перезапуска и между JVM.
Другой payload с тем же ключом отклоняется (400). Повтор возвращает **исходный ответ**,
даже если объект позднее изменён/удалён; актуальное состояние запрашивается GET.
Общего JVM-монитора и десятиминутного кэша больше нет; история автоматически не очищается.
Для запросов без ключа защита от повтора не предоставляется.

creationDate нормализуется до микросекунд до INSERT, поэтому POST и GET совпадают.
Страница списка (items, total, связанные DTO) строится в одной новой read-only
REPEATABLE READ транзакции, без блокировки записывающих пользователей.

Авторизация ограничивается отдельно по username/операции (30 в минуту), фактическому
IP (120) и высоким общим пределом процесса (1000). IP/global проверяется до чтения
тела, user quota — после bounded validation; заблокированный IP не расходует global
budget остальных. При отказе возвращается 429 и Retry-After. За SSH/NAT IP-предел общий,
лимиты локальны процессу. Политика паролей не менялась.
[Архитектура, ограничения, тесты и обновление](docs/BACKEND-FIXES-2026-11-02.md).

### Проверки

```bash
mvn test
npm ci
npm test
```

Для интеграционных проверок нужны запущенные Payara и PostgreSQL, тестовый аккаунт
и переменные `TEST_BASE_URL`, `TEST_AUTH_USER`, `TEST_AUTH_PASSWORD`, `TEST_DB_URL`,
`TEST_DB_USER`, `TEST_DB_PASSWORD`. После их настройки запустите:

```bash
mvn -Pintegration verify
```

Полный интеграционный прогон выполняйте **только на отдельном тестовом экземпляре**.
DatabaseIT, DatabaseConcurrencyIT и PaginationIT создают/удаляют свои временные схемы.
MutationApiIT и IdempotencyIT используют JDBC одновременно с HTTP, включая временное
CHECK-ограничение для проверки отката записи ответа. TEST_DB_URL и TEST_BASE_URL
обязаны указывать на одну тестовую БД/схему. Для межпроцессных повторов задайте
TEST_SECOND_BASE_URL второго Payara с той же БД и существующим тестовым аккаунтом;
без него IdempotencyIT использует независимые клиенты одного сервера.
RegistrationIT оставляет тестовые аккаунты; успешные idempotency records намеренно
сохраняются до удаления тестовой БД. Не запускайте весь набор на рабочей БД.
**На Helios полный интеграционный прогон не подходит:** создание схем запрещено.
Не направляйте DatabaseIT в рабочую схему. Отдельный запуск API-тестов описан в
[инструкции Helios](docs/HELIOS.md).

### Выводы по работе

Разработана многослойная ИС управления организациями на Jakarta EE/CDI.
JPA с провайдером EclipseLink отображает сущности и связи в PostgreSQL;
ограничения проверяются при разборе запросов, на уровне ORM и в БД.
Специальные операции выполняются функциями PostgreSQL. REST-интерфейс отделён
от бизнес-логики и репозиториев, WebSocket уведомляет клиентов об изменениях,
а optimistic locking защищает от сохранения устаревшей формы.
Подтверждены сборка WAR, 106 модульных Java-тестов, 45 интеграционных тестов
на отдельном PostgreSQL 16 и двух Payara Micro 6.2025.11/EclipseLink, 39 DOM-тестов
и 19 тестов скрипта Helios. Интеграция включает конкурентные перепривязки,
HTTP/JPA lock-before-read, атомарный merge, откаты, межпроцессную идемпотентность,
точность POST/GET и согласованную пагинацию. Отдельно проверен replay после полного
перезапуска JVM с новым входом пользователя.
Эти проверки локальные: обновление и сквозная приёмка текущей версии на Helios
пока не выполнены.
